# 原理与踩坑

本文记录**为什么这么做**，以及**哪些做法试过但失败了、根因是什么**。
只看结论很容易重走一遍弯路，所以失败方案也一并留下。

---

## 一、整体流程

```
扫描件
  │
  ├─ 1 纠斜          投影方差法，±3° 内搜索
  ├─ 2 找外框        形态学提长直线 + 多阈值降级
  ├─ 3 排除线带      去掉图廓线本身
  ├─ 4 找内容边界    墨迹密度游程
  ├─ 5 安全兜底      不可信则整幅保留
  │
  ├─ 定尺寸灰度 PNG
  │
  ├─ 6 图号→经纬度   按图集网格规则换算
  ├─ 7 写 GeoTIFF    + 金字塔
  └─ 8 建 VRT        总镶嵌索引
```

设计上有一条贯穿始终的原则：

> **宁可留白，绝不切内容。**

地图裁掉一块就永久丢失了，边缘多留几毫米只是难看。
所以每一步的"不确定"都朝保守方向倒。

---

## 二、分步原理

### 1. 纠斜：投影方差法

把图旋转到不同角度，统计**每一行黑像素数量**这个序列的方差。
图摆正时，图廓的横线落在一行里，行投影会出现尖锐的峰，方差最大。

$$\hat{\theta} = \arg\max_{\theta} \operatorname{Var}\big(\text{rowProjection}(\text{rotate}(I, \theta))\big)$$

在 1600px 缩略图上做，步长 0.02°，全程不到 1 秒。
实测能把 ±1.2° 的倾斜反解到 0.02° 以内。

### 2. 找外框：形态学长核开运算

**先说霍夫直线变换：它能用，但必须加约束。**

`cv2.HoughLines` 在密集等高线的地图上会检出成千上万条候选"直线"，
不加处理地"排序取最长那条"完全不可靠——地形图里最长的"直线"往往是一道山脊。

但需要澄清：**这不等于霍夫方法本身不可用。**
已有研究在四川省 1:10 万民国地形图上成功应用了霍夫变换完成图框识别，
其关键在于加入了**角度分类与位置约束**——把检测到的线按倾角分成水平/垂直两类，
且限定线心必须落在距边缘 15% 的区域内，以此排除地图内部的线条干扰。
（出处见项目根目录的 `简介与参考资料.md`。）

**本工具采用的做法**：二值化后用**很长的核**做形态学开运算。
长度为 `W/40` 的横向核只会保留贯穿性长直线，等高线这种短曲线全被抹掉，
然后再对投影取阈值定边界。

选它是针对**"图廓线偏淡导致单边漏检"**这一特定失败模式的处理，
并非霍夫本身不行。若换成形态学也检不出框的图集，霍夫加约束仍是一条可选路径。

**关键坑：必须多阈值降级。**
只用一个阈值时，某一边的图廓线偏淡就会只检出另外三条边，
得到一条**细条矩形**。真实案例：

| 情形 | 检出的外框 | 后果 |
|---|---|---|
| 正常 | 5800 × 4600 | 正确 |
| 单边漏检 | 4647 × **21** | 几乎退化成一条线 |
| 单边漏检 | **4** × 3718 | 同上 |

如果直接拿细条去裁，整幅图就废了。
所以检测器要求 `w > 0.4W 且 h > 0.4H 且 0.7 ≤ 宽高比 ≤ 1.9`，
不满足就降低阈值重试（0.30 → 0.22 → 0.16 → 0.12 → 0.09 → 0.07）。

这个 bug 曾导致一批图幅把标题、图廓说明一起裁了进去。

### 3. 找内容边界：密度游程

在外框内逐行逐列统计墨迹占比，做 7 点平滑，
再取"**连续 N 个像素都超过阈值**"的最外端作为边界。

`density_threshold` 与 `density_window` 是两个配合的参数：

- 阈值太低 → 把纸张噪点当内容，留白过多
- 阈值太高 → 把边缘稀疏的等高线切掉
- 连续窗口 → 抗孤立噪点，防止把一道折痕当成内容边界

## 三、失败方案与根因

### ✗ 失败一：固定密度阈值无法兼顾

**问题**：同一个阈值，对内容密的图会切内容，对内容疏的图会留大边。

不同图幅的内容密度差异极大（实测从 0.08 到 0.87，相差十倍）。
用 0.15 时，稀疏图幅的边缘（左边 673~766px、上边 942px）被当作空白切掉；
降到 0.10 救回了这些，但在密集图幅上留白依然明显。

**为什么不能做成自适应？**
试过"按每幅的密度分布自动定阈值"，结果是**所有图幅算出来的框都是整幅的
99%~100%**——因为地形图边缘总有零星注记，密度永远不会真正归零。
自适应阈值在这个数据上没有区分度。

**最终方案**：固定一个偏保守的阈值（0.10），配合安全兜底。
接受"有些图留白多一点"，换取"不会切内容"。

### ✗ 失败二：`cv2` 在中文路径下静默失败

`cv2.imread()` 遇到中文路径**不会报错，直接返回 `None`**。
如果代码里没检查返回值，就会在远处崩掉或者产出空文件。

**解决**：
```python
# 读
arr = np.array(Image.open(path).convert("L"))          # 走 PIL
# 写
cv2.imencode(".png", arr, [...])[1].tofile(path)       # 走 bytes
```

### ✗ 失败三：`gdal_translate.exe` 缺 DLL

直接从 GDAL 命令行工具调用，在部分环境下报 `0xC0000135`（找不到 DLL），
即使把 bin 目录加进 `PATH` 也一样。

**解决**：改用库调用。本工具包统一走 `rasterio`（PyPI 版自带 GDAL 二进制），
彻底回避这个部署问题。

### ✗ 失败四：纬度一变，东西向偏移就得重算

历史地图与现代底图之间有系统性偏移，用整体平移来对齐。
换算公式：

$$\Delta\text{lon} = \frac{\text{shift}_m}{111320 \cdot \cos(\varphi)}$$

**这个量依赖中心纬度 φ。** 一次操作中我们把两幅图向北移动了一个图幅，
纬度变了，但栅格的经度我按"只动南北"保留了原值，
结果**矢量图框与栅格影像在东西方向错开了约 10 米**（0.000104°）。

单幅看不出来，但在 GIS 里放大叠加就会发现。

**教训**：任何"移动图幅"的操作，都要把经、纬当作联动的整体重新算一遍，
不要只改用户口头提到的那一个方向。

### ✗ 失败五：均匀网格假设，累积偏移一整格

接图表是逐格标注图号的，看起来很规整，于是我先假设
"网格均匀铺满图框"，用 `框宽 / 列数` 当作列宽。

**结果偏了整整一列（约 60px）。**

原因：图框内还有行号栏和说明文字占用的边距，实际网格并不铺满整个框。
网格的真实间距要用**测得**的：在一行图幅全满的位置做投影，取竖线间距。

修正前后的分离度（有图格 vs 无图格的平均墨迹差）：

| 网格参数 | 列宽 | 分离度 |
|---|---|---|
| 均匀假设 | 65.97 | 9.4 |
| 实测标定 | 63.00 | **20.6** |

**教训**：扫描件的网格/图框参数一律要实测，不要从"设计值"推。
而且这个错误**不会报错**——它只是悄悄让你所有的坐标判断都偏一格。

### ✗ 失败六：比对键不一致（犯了两次）

清单里的图号是 `0119`，而成果文件名是 `0119-花凉亭_geo.tif`。
直接做集合减法，会把**全部**图幅都报成"缺失"。

这个错误我犯了两次，第二次是在"修好了第一次"之后。
所以现在把它固化成了工具：
```bash
python scripts/tools/check_outputs.py
```
`sheet_no_of()` 统一从文件名前缀解析图号后再比对。

**教训**：跨来源的数据比对，先把"键"对齐再比，
否则得到的是满屏假警报，比不检查更糟——它会掩盖真问题。

### ✗ 失败七：自动筛查一定要目视复核

用"格子内墨迹密度"自动判断"接图表上这一格有没有图幅"，
报出了一批"疑似错位"。逐条核实后发现**大部分是误报**：

| 报警来源 | 真实原因 |
|---|---|
| 墨迹 30.6% | 是"河南省/陝西省"的省界标注 |
| 墨迹 17.4% | 是图框内"全省共約五百一十幅"的说明文字 |
| 墨迹 14.5% | 是一条河流线 |
| 墨迹 7.2% | 实际有图名文字，只是字迹偏淡 |

**只有目视确认过的才是结论。**
自动筛查的价值在于"缩小需要看的范围"，不在于"给出结论"。

### ✗ 失败八：排除非图幅文件

批量脚本用 `glob("*.jpg")` 扫输入目录，把**接图表也当成一幅地图**处理了，
一路走完裁切、增强、配准，安安静静地多出几个文件，全程没有报错。

**解决**：`crop.exclude` 配置项。这是必须在开工前做的一件事。

---

### ✗ 失败九：`requirements.txt` 里的中文注释

依赖清单原本写成这样：

```
# 历史地形图批量裁切与配准工具包 — 依赖
# 说明: rasterio 是 PyPI 上自带 GDAL 二进制的发行版……
numpy>=1.24
```

文件是 UTF-8。在**中文 Windows** 上执行 `pip install -r requirements.txt` 时：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xa3 in position 24
```

**根因**：pip 在部分版本上**用系统 locale 编码（cp936/GBK）读取 requirements 文件**，
而文件是 UTF-8，中文注释就成了非法字节序列。

**这个 bug 最麻烦的地方是它会漏过测试。**
在新版 pip（如 26.x）下，requirements 按 UTF-8 读取，**完全正常**；
只有旧版 pip 或特定 locale 环境才会失败。
也就是说——**开发机上跑得好好的，到了用户机器上就装不上。**

**解决**：`requirements.txt` 改为**纯 ASCII**，注释一律用英文。
并在文件里写明"本文件不得加入非 ASCII 字符"，防止后来人又加回中文。

> **一般规律**：凡是**会被命令行工具读取**的配置文件，编码行为都不由你控制，
> 取决于那个工具的版本与运行环境的 locale。
> 这类文件（`requirements.txt`、部分工具链的 `.cfg`）保持纯 ASCII 最稳妥。
>
> 而 `.md` / `.py` / `.yaml` 这些由明确指定 UTF-8 的解析器读取的，用中文没有问题——
> 但要在文件里注明"必须保存为 UTF-8"，因为用户用记事本「另存为 ANSI」同样会踩坑。

## 四、几条通用经验

1. **不确定就倒向保守。** 这个流程里所有"拿不准"的地方都选择留白/保留，
   因为切掉的内容不可恢复。

2. **单幅试跑再批量。** 几百幅跑一遍要几十分钟，参数错了全部重来。
   三个脚本都支持指定单个文件。

3. **保留中间报告。** `crop_report.json` 记了每幅的角度、外框、比值、是否兜底。
   出问题时不用重新跑，直接查报告。

4. **测出来的值才算数。** 网格间距、偏移量、阈值——凡是能从数据测的，
   都不要用设计值或估算值。

5. **验证要看正反两面。** "检查器报 0 对"不能作为通过依据，
   必须同时确认它在**有错时能报出来**。否则你没法区分
   "真的没问题"和"检查器根本没工作"。

6. **分类不要合并。** 处理不可得的信息时，
   要区分"数据里读不出来"和"原图本来就没有"——这两者对后续决策的意义完全不同。
